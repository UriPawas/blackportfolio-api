# Portfolio Report Design

Turns the tracker's already-computed metrics into an investor-deck-quality report in **two distinct deliverables that share one data contract but are deliberately different media**:

- **PDF (vertical, formal document).** Portrait orientation, always. This is the long-form, formal deliverable — the one place the analysis is allowed to *explayarse*: full narrative paragraphs, dense tables, footnoted methodology. Rich visual design per tone (imagery, color-blocked section openers, styled charts), but the reading model is a document you study, not a deck you flip.
- **Interactive HTML (horizontal, animated presentation).** Landscape orientation, always. One full-viewport slide at a time with real motion: entrance animations (numbers counting up, bars growing, lines drawing in), hover states (chart tooltips, cards lifting, news items revealing detail), smooth slide transitions. Copy is short and punchy — headlines and key figures, not paragraphs; anything long-form belongs in the PDF. The design goal is *momentum*: each slide should make the viewer want to advance to the next.

If a build of these two ever feels like the same layout rotated, it's wrong — different orientation, different text density, different interaction model.

Both carry real Pexels imagery, AI narrative insights grounded in the specific news that moved the specific positions in the specific portfolio being reported, and model quality that scales with the user's plan without ever hard-failing on the cheapest tier. **Tone is chosen once, by the app, at generation time** (see `references/tone-selector.md`) — neither deliverable ever shows a style/tone control to the person viewing it. **All copy renders in the app's current UI language** (`currentLang` in main.js — es/en/fr) — never hardcode one language into a template.

## Before writing any code

This runs inside a real, already-functioning report pipeline — do not invent a parallel architecture.

- Read `references/architecture.md` first. It documents where the report's data comes from (`computeHistoricalReport` / `exportPortfolioPDF` in [main.js](../../../main.js)), where AI narrative comes from (`/api/ai/insights` + `models_for_plan` in [api.py](../../../api.py)), and the PDF rendering gotcha (page-break CSS must live outside `@media print`).
- The report is **always** scoped to one already-resolved `portfolio` object (has `.id`) belonging to the authenticated `uid`. Never aggregate across a user's other portfolios, never trust a client-supplied portfolio/user id for data selection — follow the same server-verified-ownership pattern the rest of the API already uses (Firebase ID token → uid → row ownership check).
- Confirm with the user which surface is being touched — the existing PDF export, the not-yet-built interactive HTML view, or both — before large rewrites. They're two renderings of the same data contract, not two separate features to build in parallel by accident.

## Workflow

1. **Map metrics to the data contract.** See `references/data-contract.md` — it mirrors the real `computeHistoricalReport` return shape (not an invented generic one). If a report needs a field that shape doesn't produce, say so and ask rather than fabricating numbers.
2. **Pick a tone.** Default is **`brand`** — BlackPortfolio's own palette (`--primary: #6f86ff` / `--primary-strong: #556eff` / `--accent: #7892ff` from styles.css), so a report with no tone chosen looks like *this app*, not like Nu or any reference deck. The five deck-derived presets (AMD, Grupo Bimbo, American Express, JPMorgan, Nu Holdings — see `references/design-system.md`) are opt-in alternates. Each tone is a CSS token set (`assets/tone-tokens.css`) plus an AI voice modifier — same data, different presentation. A future in-app customization section will let users adjust the palette themselves (see `references/tone-selector.md`); design token usage so that swap is trivial.
3. **Fetch imagery via Pexels — the key exists, use it.** `PEXELS_API_KEY` is configured on the Railway service `blackportfolio-api` (api.py already proxies Pexels at `/api/gallery`); run generation-time fetches through `railway run --service blackportfolio-api -- python scripts/fetch_pexels_images.py` so the secret is never printed. Queries derive from the portfolio's dominant sectors (`SECTOR_QUERIES` in that script) and stay generic/financial/architectural. Never search for or use images of identifiable real people. Cache by query; never refetch per render. Credit the photographer (Pexels license). A deck with zero imagery is a failed build unless the tone is `minimal`.
4. **Fetch position-level news.** `scripts/fetch_position_news.py` — for the report's top 3 positive and top 3 negative contributors (by `periodPnl`/attribution pp, skip anything under ~0.5pp as noise), pull recent headlines via `yfinance` (`Ticker.news` — already a project dependency, **no new API key needed**), including each item's `summary` and `url` and the ticker's next earnings date. See `references/news-research.md` for selection/caching rules.
5. **Turn news into insight, then generate narrative.** Headlines alone are not a deliverable — `references/market-narrative.md` defines the required structure per mover (**evento → mecanismo → impacto cuantificado en este portafolio → a vigilar**, every bullet anchored to a figure from the data contract, money before percent). Extend the existing `/api/ai/insights` system prompt in api.py — don't replace its rigor rules (money-before-percent phrasing, materiality thresholds, forbidden generic advice, Sharpe/Sortino/HHI/beta interpretation ranges already encoded there). Add: (a) the tone's voice modifier, (b) the fetched news as the *only* admissible source for causal claims, (c) the mover-card JSON shape so the deck gets bullets, not prose. Keep reusing `models_for_plan(plan)` — see `references/model-tiers.md` — and keep the deterministic metrics-only fallback so the "qué movió al mercado" section always renders.
6. **Render — two separate templates, tone baked in, never a switcher in the output.** Tone is resolved to a fixed `data-tone` value **before** rendering (an app-level generation parameter — see `references/tone-selector.md`); the rendered artifact contains zero UI for changing it. All static strings come from a per-language string map keyed by the app's `currentLang` (es/en/fr — main.js ~14796), and the AI narrative is requested in that same language via the existing `lang` param of `/api/ai/insights`. The two renderers:
   - **PDF — vertical formal document. `references/pdf-document.md` is the binding spec; read it before writing a line of the document.** It fixes the six failures of the shipped export: content cut across page boundaries (solved by a fixed-page model + measured pagination, *not* by `page-break-inside` hints), dashboard-dump structure, zero photography, one font and one accent, sections that print regardless of relevance, and hardcoded Spanish. Start from `assets/pdf-shell.html` + `assets/pdf-paginate.js` + `assets/pdf-charts.js` — they already implement the 794×1123 page model, the pagination engine with splittable tables, the print type scale, the section accent rotation, the seven image/text patterns and the eight static print charts. Stays a client-side render via the existing `html2pdf.js` pipeline (`_loadHtml2Pdf` in main.js) — don't introduce a Python/headless-browser render path there.
   - **Interactive HTML — horizontal animated presentation.** **`references/html-presentation.md` is the binding spec; read it before writing a line of the deck.** It fixes the five failures of the first builds: a fixed 1600×900 stage (kills tiny type), an explicit type scale with attention devices, the 4-layer slide grammar and ≥78% fill rule (kills dead whitespace), hand-rolled animated SVG charts instead of library defaults, and the entrance choreography. Start from `assets/deck-shell.html` + `assets/deck-charts.js` — they already implement the stage, navigation, count-up, reduced-motion and the eight chart renderers. Copy is compressed to headline + key figure; the viewer who wants depth downloads the PDF.
   Both read the same data-contract JSON and the same tone token set — but they are different markup, different text density, different orientation, different interaction model. If they ever look like the same layout rotated 90°, the build is wrong.
7. **Validate before calling it done.** For the PDF, run the 12-point QA gate at the end of `references/pdf-document.md` — items 1 and 2 are assertions you run in code, not judgement calls: every `.page-body` must satisfy `scrollHeight <= 1000`, and `pdf.internal.getNumberOfPages()` must equal the number of `.page` elements. For the deck, run the 12-point QA gate at the end of `references/html-presentation.md` — it is not optional, and items 1–4 (no type under 16px, no "—"/N/A cells, 4-layer grammar + ≥78% fill, entrances firing on activation) are exactly what failed review before. Render with at least two different portfolios (different holding count, a losing period, a portfolio with no benchmark) and at least two tones, and confirm it still works when `models_for_plan` resolves to the cheapest tier (simulate an Explorer-plan user) and when Pexels/OpenRouter/news calls fail outright — the report must still render with graceful fallbacks, never a blank page or a hung spinner (see the existing try/finally-without-catch footgun noted in `references/architecture.md`). Also verify every currency figure via `getPosCurrency`-equivalent logic (see `references/architecture.md`'s FX section) — check the total against what the user actually sees in the live dashboard for that portfolio, not just against the position's stored `currency` field.

## Key constraints

- **Adaptive, not personalized-by-hardcoding.** Nothing about a specific user's tickers, balances, name, or portfolio id belongs in template/script source — everything is per-render data.
- **Scoping is non-negotiable.** One portfolio, one owning uid, verified server-side. This is the difference between a report and a data leak.
- **No style controls inside the artifact.** Tone selection happens once, in the app's report-generation flow, before rendering. Neither the PDF nor the interactive HTML ever shows tone/style switching UI to the viewer — an in-artifact tone switcher is a testing/evaluation convenience only, never a shipped feature.
- **PDF and HTML are not the same template.** PDF = **vertical** formal document (portrait pages, long-form prose, complete tables, footnotes — the place to explayarse). HTML = **horizontal** animated presentation (landscape slides, headline-and-figure copy, motion and hover throughout). Don't build one and derive the other by mechanical print-CSS or rotation — they read the same data contract but are written and laid out for their own medium.
- **The deck's quality bar is objective, not taste.** Fixed 1600×900 stage, nothing under 16px, ≥78% content fill with the 4-layer grammar, hand-rolled animated SVG charts (no library defaults), real imagery unless the tone is `minimal`, and every mover carrying a quantified portfolio impact. All of it is checkable — see the QA gate in `references/html-presentation.md`.
- **Language follows the app.** Every static string comes from an es/en/fr map selected by `currentLang`; the AI narrative uses the same `lang`. A report that hardcodes Spanish for an English-UI user (or vice versa) is a broken build.
- **Default look = BlackPortfolio brand, not a reference deck.** The `brand` tone (app palette `#6f86ff`) is the default; Nu's purple (`gradient`) and the other four deck tones are explicit opt-ins. Reports must never leak a reference company's identity as the app's default face.
- **Currency is never read from `pos.currency` alone.** Always resolve via the ticker-suffix-first rule (`getPosCurrency`/`detectCurrencyFromTicker` in `references/architecture.md`) before computing any value/P&L figure. Getting this wrong produces numbers that look plausible but are off by an order of magnitude — verified the hard way in the jul-2026 evaluation.
- **Secrets stay in env vars.** `PEXELS_API_KEY`, `OPENROUTER_API_KEY` never appear in committed source, templates, or logs.
- **Graceful degradation everywhere.** Pexels fails → gradient/solid cover. News fetch fails or finds nothing → omit that ticker's news, never invent an event. AI call fails on every model in the chain → fall back to the tracker's own numbers with a visible notice, exactly like the existing `aiError` block does today.
- **Don't duplicate the model-routing system.** `models_for_plan` in api.py already does per-plan model selection with graceful downward fallback. Reuse it.

## Reference files

- `references/pdf-document.md` — **binding spec for the PDF**: fixed-page model + the html2pdf settings that actually map 1:1, the pagination engine contract, print type scale and typographic devices, paper palette + section accent rotation, the seven image/text patterns, the 16–24 page outline with eligibility rules, the narrative depth budgets, print charts, tables, QA gate.
- `references/html-presentation.md` — **binding spec for the interactive deck**: stage model, type scale, density/slide grammar, slide outline + metric-selection rules, the eight chart renderers, motion choreography, Pexels usage, QA gate.
- `references/market-narrative.md` — how "qué movió al mercado" becomes insight: the four-bullet mover card, quantification rules, enrichment fields, AI prompt shape, deterministic fallback, anti-patterns.
- `references/architecture.md` — where the real report data, AI insights endpoint, and PDF pipeline live today; the scoping, FX and page-break gotchas; how to get the Pexels key without printing it.
- `references/design-system.md` — five tone presets (palette, typography, imagery density, layout anatomy, copy voice) extracted from visual analysis of AMD, Grupo Bimbo, American Express, JPMorgan Chase, and Nu Holdings investor decks.
- `references/data-contract.md` — the JSON shape mapped from `computeHistoricalReport`'s real return fields, plus the `news` and `tone` additions.
- `references/news-research.md` — how to pick which positions get news, how to fetch it for free via yfinance, caching, and how to feed it to the AI prompt without bloating it.
- `references/model-tiers.md` — how to keep AI output usable across the existing Explorer → Wealth Desk model chain.
- `references/tone-selector.md` — forward-looking spec for the in-app tone-selector UI (not built yet); what it needs to control and where it plugs in.
- `assets/tone-tokens.css` — CSS custom-property sets for the tone presets (including semantic `--tone-up`/`--tone-down`), applied via `data-tone` on the report root.
- `assets/pdf-shell.html` — runnable PDF skeleton: 794×1123 pages, cover/opener/closing bleeds, narrative page with drop cap + sidenote rail + duotone band, mover cards, position dossiers, splittable tables, glossary, dev audit bar and the export call. Copy it and replace `REPORT` + `STR`.
- `assets/pdf-paginate.js` — the pagination engine: readiness gate (fonts + image decode), atom/split/table/keep-with-next contract, table continuation with repeated headers, running chrome, and the overflow assertions behind QA items 1 and 2.
- `assets/pdf-charts.js` — the eight static print charts (equity, waterfall, diverging, donut, bars, underwater, sparkline, monthly), authored 1:1 at the slot width with deterministic heights so pagination can measure them.
- `assets/deck-shell.html` — runnable deck skeleton: 1600×900 stage, navigation (keys/wheel/swipe/dots/hash), entrance choreography, count-up, reduced-motion, one example of every chart. Copy it and replace `DECK_DATA` + `STR`.
- `assets/deck-charts.js` — the eight animated SVG chart renderers (area, waterfall, diverging, donut, gauge, sparkline, underwater, stacked). No dependencies; colors read from tone tokens; `_play()` fires on slide activation.
- `scripts/fetch_pexels_images.py` — Pexels search/download/cache helper.
- `scripts/fetch_position_news.py` — yfinance-based per-ticker headline fetcher for top movers.
